# CampusSkill — Development Rules

## Purpose

These rules define how AI agents and developers must work on the
CampusSkill project.

The project must be developed in small, controlled, testable steps.

---

## Rule 1 — Protect Product Requirements

Never change a confirmed product requirement without explicit
approval from the Product Owner.

---

## Rule 2 — Read Project Documentation First

Before making significant changes:

1. Read PROJECT_CONTEXT.md.
2. Read PRODUCT_REQUIREMENTS.md (mandatory for institution-specific, configuration, branding, module-flag, or multi-tenant changes).
3. Read relevant project specifications.
4. Inspect the existing implementation.
5. Understand dependencies and existing functionality.

Do not make assumptions when the required information already exists
in project documentation.

---

## Rule 2b — Configuration over customization

Prefer existing configuration over source-code changes when an institution
request differs only in identity, branding, academic structure, modules,
or normal institutional rules.

Classify every institution request per `PRODUCT_REQUIREMENTS.md`
(configuration / existing module / reusable feature / institution-specific
extension / unsupported) and obtain Product Owner decision before building
custom code. Institution admins must not modify schema, platform permissions,
or core security logic.

---

## Rule 3 — Small Changes

Make the smallest appropriate change needed to complete the task.

Avoid changing unrelated files or features.

Prefer small, reversible changes over large uncontrolled changes.

---

## Rule 4 — Do Not Break Existing Functionality

Never remove or modify working functionality merely to solve an
unrelated problem.

Before changing existing functionality, inspect how it currently works.

---

## Rule 5 — Security

Never expose API keys, passwords, tokens, database credentials or
other secrets in frontend code or committed files.

Secrets must use environment variables or secure secret management.

---

## Rule 6 — Authentication and Authorization

Protected functionality must verify authentication.

Authorization must also be checked.

Students must not be able to access another student's private data.

Faculty must only access data they are authorized to access.

Admin permissions must be explicitly controlled.

---

## Rule 7 — AI Provider Independence

Do not permanently hard-code the application around one AI provider.

AI functionality should use a service abstraction or gateway where
practical so providers can be changed or added later.

---

## Rule 8 — AI Evaluation

AI-generated scores and evaluations are assessments generated by the
system.

They must not automatically become officially verified student
competencies.

Formal competency verification may require faculty or authorized
institutional verification.

---

## Rule 9 — Reusable Architecture

Use modular architecture.

Reuse components, services and utilities when appropriate.

Do not create duplicate components or duplicate logic unnecessarily.

---

## Rule 10 — User Experience

Major features should provide appropriate:

- Loading states
- Empty states
- Error states
- Success states

The interface must remain understandable to students and faculty
without technical knowledge.

---

## Rule 11 — Data Validation

Validate user input and database operations.

Never assume that frontend validation alone is sufficient.

Server-side validation must be used where applicable.

---

## Rule 12 — Dependencies

Do not add unnecessary packages or libraries.

Before adding a dependency, determine whether the existing project
already provides an appropriate solution.

---

## Rule 13 — MVP Priority

Prioritize the smallest useful working MVP.

Do not add advanced features simply because they are technically
possible.

Do not build future-phase functionality before the current phase is
validated.

---

## Rule 14 — No Premature Features

Do not implement the following during the initial MVP unless
explicitly approved:

- Recruiter marketplace
- Advanced recruiter portal
- Full internship management
- Advanced portfolio
- Job matching
- Payment system
- Android application
- Advanced institutional analytics
- Complex multi-agent AI system
- Large-scale multilingual content system

---

## Rule 15 — Testing

Before considering a major feature complete:

1. Run relevant tests.
2. Run the application/build.
3. Check for errors.
4. Test the main user flow.
5. Check for regressions.

Never claim that a feature works unless it has been tested.

---

## Rule 16 — Documentation

Important technical or product decisions must be documented.

Update relevant documentation when implementation changes make the
documentation inaccurate.

---

## Rule 17 — Change Log

Maintain a CHANGELOG.md file once implementation begins.

Record meaningful completed changes.

---

## Rule 18 — Git Commits

Use meaningful commits.

A commit should represent a logical completed change.

Avoid vague commit messages such as:

- update
- changes
- fix stuff
- final

Prefer messages such as:

- Add student authentication
- Create case study model
- Add AI evaluation service
- Fix student dashboard loading state

---

## Rule 19 — Ambiguity

When a requirement is unclear, do not silently invent an important
product decision.

Identify the ambiguity and classify it appropriately.

---

## Rule 20 — Requirement Labels

Use these labels in project documentation:

[CONFIRMED]
Confirmed product requirement.

[ASSUMPTION]
Temporary assumption that has not been confirmed.

[NEEDS DECISION]
Requires Product Owner approval.

[TECHNICAL RECOMMENDATION]
Technical recommendation from the development agent.

---

## Rule 21 — Product Owner

The founder is the Product Owner and academic subject-matter expert.

The Product Owner makes final decisions about:

- Product requirements
- Academic content
- Target users
- Business model
- Institutional workflows
- Major product changes

AI agents provide recommendations but must not silently change these
decisions.

---

## Rule 22 — Explain Important Technical Decisions

When a technical decision requires Product Owner approval, explain it
in simple language before proceeding.

Avoid unnecessary technical jargon.

---

## Rule 23 — Research Before Major Decisions

For major technical, product or business decisions, research reliable
sources before implementation when current information is required.

Clearly distinguish:

- Facts
- Assumptions
- Recommendations
- Open decisions

---

## Rule 24 — No Uncontrolled Autonomous Development

AI agents may work autonomously only within the approved scope.

They must not independently redesign the product, change confirmed
requirements or introduce major features without approval.

---

## Rule 25 — Completion Standard

A task is complete only when:

- The requested functionality is implemented.
- Relevant tests have been performed.
- The application builds or runs successfully where applicable.
- No known critical error remains.
- Relevant documentation is updated.
- The change is committed to Git.

---

## Rule 26 — Development Sequence

Follow the approved development sequence:

1. Product specification
2. Research
3. Technical architecture
4. Project foundation
5. Authentication
6. Student MVP
7. AI evaluation
8. Skill Passport
9. Faculty MVP
10. Testing
11. Pilot
12. Business validation
13. Institutional version
14. Internship module
15. Recruiter module
16. Android application

Do not skip directly to later phases without approval.

---

## Rule 27 — Current Priority

The current priority is to establish the project foundation,
documentation, architecture and development rules.

Application implementation must begin only after the required
planning documents have been reviewed and approved.

---

## Rule 28 — Quality Over Speed

Do not sacrifice security, correctness or maintainability merely to
produce code faster.

Build slowly enough to understand what is being created.

---

## Final Instruction

Before every significant implementation task:

Read the project context.
Read PRODUCT_REQUIREMENTS.md (institution / multi-tenant / configuration).
Read the relevant specifications.
Inspect existing code.
Make a small change.
Test it.
Document it.
Commit it.

CampusSkill must evolve through controlled, measurable milestones.
